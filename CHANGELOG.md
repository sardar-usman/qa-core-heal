## 0.3.4 (unreleased)

**Three message-level fixes from the 0.3.3 transcripts.** (1) Nameless-candidate teaching: when a near-miss refusal's top candidate is DEFINITELY an icon-only interactive control with no accessible name (no text, no aria-label/labelledby, no title, no associated label, no value — computed from the DOM read, never guessed), the refusal teaches instead of just scoring: `closest candidate #buttonGenerate is an icon-only button with no accessible name; a role-and-name locator cannot target it (add an aria-label, or target it by id)`; and when an unverifiable-kind refusal's candidate is an anchor WITHOUT href (definitely not exposed as a link, per ARIA), it appends `closest match is an anchor without href, which is not exposed as a link; target it by title or id, or give it an href`. The `#wipeAllButton` nameless-refusal pin is unchanged — it flows through a different branch (the parked-nameless gate, no closest candidate) and its button carries emoji text, so it is not icon-nameless; no other pinned refusal fixture contains either shape. (2) The iframe note prioritizes same-origin frames: cross-origin widget frames (the GitHub-Star shape — they can never hold the app's element) are omitted when same-origin frames exist, and reported count-only (`this page embeds N cross-origin widget iframe(s) …`) when they are all a page has; the /upload same-origin note is byte-identical. (3) The revert count line matches the per-heal classification: all-non-locator reverts say `N heal(s) reverted: the re-run still fails for a non-locator reason`, mixed reverts carry both counts, and all-locator reverts keep the original wording (scenario 24 byte-identical, scenario 30 pins the new summary). Pinned red-first: the icon-only near-miss, the no-href anchor refusal, and the mixed same+cross frames note naming only the same-origin src.

**Emitted identity is read from the confirmed element, never copied from the broken locator.** Field bug (/visibility): `page.locator("#removed")` — a truncation of `#removedButton` — healed to `getByRole("button", {"name":"removed"})`: the ladder resolved the button through Playwright's SUBSTRING name matching using the broken token, then emitted that token — green re-run, fragile locator (the real name is "Removed", the element has a stable id, the emit was neither; earlier sheet rows `{"name":"Hidde"}` and `{"name":"nam"}` are the same shape). New emit contract for every name-carrying ladder level (role/label/placeholder/text/title), aligning with the fuzzy path which already emitted full names: (1) a broken css original whose confirmed element carries a stable id — stable meaning NO generated segment; `#digest-checkbox-1f8a2e` rotates per deploy even though half of it is human — prefers the id heal (same locator family, strongest identity); (2) otherwise the element's own full computed value with `exact: true` (accessible name from aria-label / aria-labelledby / associated label / text / title / button value; getByLabel/getByTitle/getByPlaceholder/getByText gained exact emit forms); (3) neither readable → the bare-role emit, which the nameless gate refuses with its teaching message (a token-only heal is the less-identity violation in disguise). Every rebuilt emit is count-checked to exactly one — in the RESOLUTION's frame scope, so frame-resolved heals (`frameLocator(…).getByRole(…)`) rebuild correctly instead of falling to a false refusal — and a failed check falls through, never emitting a token. Kind guard, confirmation, and ambiguity rules unchanged. THE PIN SWEEP IS THE RELEASE NOTE: 24 pinned emits across unit tests and suites changed, every one strictly more specific (token names → stable ids: `#quantity`, `#quantity-field`, `#confirm-order`, `#do-register`, `#Email` on the live shop; token names → full names with exact — "Save preferences", "Weekly digest", "Update card" in its frame, "Help center", "Archive order", "Plan selector"; substring text/label emits → exact forms), every re-run green, zero pins became less specific and zero flipped to refusals (one early candidate flip — the frame-scoped update-card — was a scope bug in the count-check, found and fixed during the sweep, not accepted). One fixture changed by design: the rot page's button id gained a generated segment so the aria-label heal that scenario rot-tests is still the winning emit. Pinned fresh: the field css shape (`#removed` → `page.locator("#removedButton")`), the role variant (`{"name":"Removed","exact":true}`), and the nameless variant (class-only confirmable element → the nameless teaching refusal).

**A heal rewrites every identical occurrence within the failing test.** Field bug (full transcript): a test used the same broken literal twice inline — run-first matched the failing call from the stack, healed ONLY that occurrence, the verify re-run failed on the second still-broken copy, and the per-test revert undid the correct heal, leaving the file broken on every run. The revert contract behaved correctly; the heal scope was the defect. A matched heal now applies to EVERY structurally identical occurrence (same canonical method + args, the existing comparison) within the failing test's own body — the body span comes from the Playwright report's test declaration lines (a test's span ends where the next declaration in the file begins) — plus the matched call's definition when it lives in a page object (a single definition, unchanged behavior). It is never wider: an identical literal in another test heals via THAT test's own failure in the same run, and passing tests' code is never touched. The scope is reported honestly — one heal, N occurrences (`healed to X (level=…, 2 occurrences in this test)`), the proposed-diff block and dry-run show every changed line, `--json` verdicts carry `occurrences: N` (additive), and consent invariance holds: the previewed plan lists all N edits and apply writes exactly those. A reverted heal is undone at every occurrence it rewrote. Pinned by run-mode scenarios: the field shape (red-first: one occurrence healed then reverted, file left broken; post-fix one heal, two edits, verify green, exit 0, zero broken copies, the near-identical-but-different literal beside them untouched) and the two-failing-tests twin (each heals via its own failure, no cross-test expansion); the POM single-definition scenario is unchanged, and no pinned diff output changed (single-occurrence formatting is byte-identical).

**Node 25: the hooks thread filters its own loader warnings.** Environmental, surfaced by the Node 23 → 25 upgrade and reproduced on the unchanged 0.3.3 build: Node 25 emits `ExperimentalWarning: stripTypeScriptTypes…` from the module-hooks THREAD, whose stderr relay can bypass or race the main thread's warning line filter, leaking loader noise into runs that must be warning-free. The hook itself now wraps its own thread's `process.emitWarning` with the same loader-noise families — only our hook and Node's module machinery run on that thread, user code never does, so the conservative guarantee (user warnings always pass through) is untouched.

## 0.3.3 (2026-08-22)

The decoy release, driven by the team's third structured testing round against uitestingplayground. The headline: five field cases where a page's own text was an exact-match decoy for a broken locator (a heading literally named "Alerts", instruction paragraphs containing "Login") now heal to the real control, because kind-vetoed resolutions stash instead of terminating, the same structural fix 0.3.2 applied to confirmation mismatches, completed for the kind guard. Around it: revert messages now say when the heal was probably right and the test itself is the problem, refusals on pages with iframes explain that the element may live inside a frame the probe cannot scan, text composed across inline child elements is collected as one candidate, and shadow-DOM role healing is investigation-verified and pinned. Three of the round's filed findings turned out to be stale-build artifacts already fixed on 0.3.2, which produced a new process rule: sheet findings recorded on older builds are re-run on the current build before they count. The eval harness closes the release at 68/68 heals, 28/28 refusals, 10/10 intact locators kept across 16 suites (157 locators, 96 deliberately broken), 30 run-mode scenarios, and zero wrong heals.

**Text composed across inline children is one candidate.** Field case (/verifytext, reproduced on a byte-for-byte copy of the live page's markup): the greeting is authored as `Welcome <span>UserName</span>!`, so the full string "Welcome UserName!" exists on no leaf element, the pool held only the inner fragment, and a one-edit typo refused at 0.50 instead of scoring ~0.93. The text scan now lets a parent contribute its composed `textContent` as a single candidate when every child is a childless inline text-level element (span, b, i, em, strong, u, small, sub, sup, mark, abbr, time, wbr, br). Every contamination guard applies unchanged to the composed value: the 80-character cap keeps prose out, `code`/`pre`/`kbd`/`samp` are not in the allowlist so a parent containing code samples never composes, block containers and mixed structures still never aggregate, and no scoring, coverage, or NAME_ISH rule was touched. The field typo now heals to `page.getByText("Welcome UserName!", { exact: true })` (the exact form arriving via the existing substring-ambiguity fallback, since nested containers share the normalized text) with a green re-run proving the emitted locator resolves uniquely. Pinned red-first on the verbatim fixture, whose own code samples double as a live contamination guard; one sheet discrepancy reported honestly: the "Hello UserName!" decoy from the team's sheet no longer exists on the live page, and the decoy-never-wins property stays pinned on the modeled fixture that keeps it.

**Shadow-DOM role healing is verified and pinned, no live bug.** The sheet reported `getByRole('button', { name: 'Generate GUIDD' })` refusing "not found" on /shadowdom while a css selector healed into the same open shadow root. The investigation disproved all three suspected mechanisms directly: the shadow scan collects names and leaf text in the same per-root loop as ids and classes (the 0.2.1 contract holds in the code as written), accessible-name identities match into open roots empirically (the exact field mutation heals at 0.92 to the named role locator, an aria-label shadow button at 0.93, leaf text two roots deep at 0.92), and the route question was moot on one fixture. The field row was recorded on an older build, where the since-fixed terminal-verdict family could kill the run before fuzzy ever saw the shadow candidate. No source changes; the role-name typo heal into an open root is now regression-pinned end-to-end, with the healed click piercing the root as the proof.

**Refusals on framed pages say so.** Field root cause (uitestingplayground /upload): the page embeds its playground in an iframe, so the Upload button and file input live in a frame the top-document candidate scan never sees, and the refusals named only outer-page text with no explanation. The probe now records the iframes of each probed document, and not-found and below-threshold refusals on such pages append: "note: this page embeds N iframe(s) (src, ...) the probe does not scan; the element may live inside one. Frame-scoped locators cannot be healed - verify the locator inside its frame manually" (sources capped at 3, both scan and run modes). Frame-context healing stays out of scope by the emit doctrine, since it would require emitting chained frameLocator locators. Pages without iframes are byte-identical by construction, and the pin review confirmed zero existing refusal pins change: the two fixtures that already embed iframes pin heals only, so no pinned string gains the note.

**Revert messages classify why the re-run still failed.** Field case: the correct heal `#inputFeld` to `#inputField` was applied, the test's own assertion was independently wrong, the verify re-run failed, and the revert message implied the heal was bad. The revert contract is unchanged (still reverted, sources byte-identical, exit 1), but the re-run failure is now classified with the existing failure classifier: when it no longer fails for a locator reason, the message says "heal reverted: the re-run still fails, but no longer for a locator reason (failure line). The heal may be correct; the remaining failure looks like a test or app problem." A re-run still failing for a locator reason keeps today's message. Both the audit entry and the `--json` verdict carry `revertReason: "locator" | "non-locator"` (additive within schemaVersion 1). Pinned as run-mode scenario 30 (correct heal, wrong assertion: classified message, non-locator reason in audit and JSON, sources restored, exit 1), the counterpart to scenario 24's locator-reason branch, whose fixture was adjusted (an empty stray element removed) so it keeps testing the branch it was built for.

**Kind-vetoed resolutions stash, a kind tiebreaker resolves decoy bands, and content kinds are named.** Field-proven across five sheet cases (Alerts, Stopp, Login, Click mee, Dynamic IDs): documentation-style pages contain an exact-text decoy for the broken token (the page heading "Alerts" exactly matches the broken name), the decoy wins the intent ladder, fails the kind guard, and that verdict was terminal, so the fuzzy stage never ran and the real same-kind control one edit away was never proposed, the same structure the 0.3.2 stash fixed for confirmation mismatches. Three coordinated pieces, because the stash alone was not enough (with the veto stashed, the decoy re-enters the fuzzy band at 1.0 beside the real control and the band goes ambiguous): (1) a kind-vetoed intent-pass resolution is stashed, never terminal, with `roleCorrected` staying exempt; (2) a kind tiebreaker in the fuzzy band, deliberately a tiebreaker and not a pool pre-filter, applied only to multi-candidate bands after the exact-equality tiebreak, dropping candidates whose kind definitely conflicts with the original locator's declared expectation, so single-candidate verdicts and near-miss evidence are untouched (a pre-filter would have silently flipped the pinned `#export-button` kind-mismatch refusal into a generic not-found); (3) only a confirmed and kind-clean fuzzy heal outranks the stash, so every pre-fix refusal returns byte-identically where no valid alternative exists. The kind table also grew: `p`, `li`, and `span` are definite content kinds (refusals now say "candidate is paragraph" instead of "cannot be verified"), role attributes still win over tags, and `<a>` with href is a definite link while a no-href anchor stays unverifiable, which is ARIA-correct. Pinned by the new decoy-pages suite (heading, list-item, and paragraph decoys beside one-edit same-kind controls, red-first 0/5 then 5/5 at role level with green re-runs), with the kind-guard suite byte-identical and zero pin flips across all 16 suites.
