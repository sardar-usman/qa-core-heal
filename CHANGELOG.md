# Changelog

## 0.3.1 (29-07-2026)

**Chained and dynamically built locators get honest teaching messages.** Field case (Mac, POM repo): two `locator('option')` failures ended as "could not be matched to source … This is a bug worth reporting" over a "scanned 0 locator(s)" line. The investigation reproduced three shapes: a VARIABLE-BUILT selector (`this.page.locator(OPTION_TAG)`) is the field case — the runtime value matches no literal call, and the old message wrongly claimed a tool bug; a CHAINED locator (`this.page.locator('#country').locator('option')`) was quietly WORSE — the extractor truncated Playwright's full-chain rendering to the base call, which matched the base literal, probed it, and reported a false "1 intact" while the test stayed red; literal calls were fine (no parser bug), and the scanned-count line is truthful (it counts probed locators). Fixes: extraction now follows chain links (`.locator`/`.getBy…`/`.filter` make a chain; positional `.first()`/`.nth()`/`.last()` alone do not — their bases stay matchable and healable exactly as before), chained targets are never structurally matched, and unmatched targets are shape-classified from the source lines their stack points at (with a sources-wide fallback for POM getters the stack skips). Both shapes now report: "this locator appears to be built by chaining (a .locator()/.getBy…() call on another locator)" / "dynamically (a variable, template, or concatenated selector)"; "only literal top-level locator calls (page.locator('…'), page.getByRole(…)) can be matched and healed" — exit 0, a documented limitation, with `--json`'s `unmatchedFailures` carrying `shape` and only unknown-shape unmatched counting into `summary.errors`. "This is a bug worth reporting" (and its exit 1) now fires ONLY when a literal, matchable-looking call genuinely failed to match. Pinned by two run-mode scenarios (chained POM, variable-built POM), extraction unit tests, and the existing literal heal scenarios as the control.

**Windows: spec filters reach Playwright in a form it can match.** Field bug: `qa-core-heal tests/systematic/1-dynamic-ids.spec.js` echoed the target with backslashes and the child Playwright run reported no tests, while a direct `npx playwright test` ran 5 in the same repo. Confirmed root cause: internal path handling built child file filters with `path.relative` — backslash separators on win32 — and Playwright matches CLI file filters against FORWARD-SLASH paths on every platform, treating them as regex fragments, so `\1` in a path is a backreference and a backslashed filter can never match. The boundary audit also found (empirically, pinned by tests) that raw filters containing regex-significant path characters were already broken on every platform: a Next.js-style bracket dir (`tests/[id]/…`) is a character class and a paren dir (`(group)`) is a regex group — both matched 0 tests raw. Every path crossing into the Playwright child (the initial run, the combined verify re-run, the per-test revert re-runs, scan-mode verify) now goes through one boundary helper that normalizes to forward slashes on every platform AND regex-escapes the filter — escaped filters match ordinary, bracket, and paren paths alike; internal fs operations keep native separators. The "Running \<target\>" echo now prints exactly what the user typed (their separators, their form), never a converted path. Pinned: a win32-style input produces a forward-slash, regex-safe filter with no backslash preceding an alphanumeric; bracket and paren dirs demonstrably fail raw and match escaped; a nested spec's filter reaches the child in escaped forward-slash form; the zero-flag output snapshot is unchanged.

## 0.3.0 (2026-07-27)

A field-testing release: five bugs found by real-world team testing are fixed — the directory-target crash (EISDIR), ESM config loading silently downgrading probes, fuzzy-candidate contamination from selector strings displayed on pages, the consent invariance violation (--yes could gate a re-probe that changed verdicts), and the quiet keep-on-failed-verify replaced by revert-on-failed-verify — plus a full CLI flag surface with a versioned `--json` contract (schemaVersion 1), Windows support for the internal Playwright run, and hardened refusal messages throughout. The eval harness closes the release at 53/53 heals, 21/21 refusals, 9/9 intact locators kept across 13 suites (120 locators, 74 deliberately broken) and 24 run-mode scenarios. The safety claim, stated precisely: zero wrong heals survived — one wrong proposal was applied, caught by verification, and automatically reverted, which is the new revert contract working as designed.

**The npx fallback announces itself.** When a child Playwright run cannot resolve the project's local `@playwright/test` CLI and drops to the PATH-dependent `npx` fallback, one stderr line says so — `using npx fallback: local Playwright CLI not resolved` — once per process; the direct local-CLI path never prints it. Both sides are pinned by tests.

**A heal that fails verification is reverted, loudly.** Field case: a heal was applied, the verify re-run failed, the audit quietly recorded `verified: false` — and the modified file was kept. New contract: when verification still fails, the edit is UNDONE (the file returns byte-identical), the run states `heal reverted: re-run still failing after heal` per heal plus a count line, the audit entry keeps the full history (`applied: true, verified: false, reverted: true`), `--json` verdicts carry `reverted`, and the exit code is 1 — an unresolved failure, not a quiet success. Granularity: run-first mode verifies PER TEST — when the combined re-run fails, each previously failing test is re-run individually and only the heals whose tests still fail are reverted, while heals whose tests pass stay and are individually verified (an improvement over the old all-or-nothing `verified` flag); a heal that cannot be mapped to a test is reverted conservatively. `--scan` mode has no per-test signal, so its granularity is per spec: a heal is reverted when any spec owning its file still fails. Pinned by a run-mode scenario whose heal is right by identity but wrong for the test (the healed button never satisfies the assertion): sources hash-identical after the run, the revert message printed, the audit triple recorded, `reverted` visible in `--json`, exit code 1 — with the existing verified-heal scenarios unchanged.

**Selector strings displayed on a page are never fuzzy candidates.** Field refusal on a documentation-style page (uitestingplayground's /classattr): `[aria-label="Button"]` refused as "ambiguous: several close matches" naming two XPATH SELECTOR STRINGS and an instruction sentence as candidates. The trace proved the pool was never contaminated by source files — `matchFuzzy`'s only feed is the live-page scan — but such pages DISPLAY selectors as code-sample text, and two changes had compounded to let that text score: single-attribute selectors gained a fuzzy identity (the 0.2.1 prefix work), and leaf-text containment needed no word coverage, so any sentence or code sample containing the token as a whole word scored 0.9. Three fixes: selector-shaped text (XPath `//…`/`[@attr]`, `xpath=`/`css=`, css-shaped tokens) is excluded from candidacy entirely — never matched, never named; raw leaf text now falls under the same ≥half-word-coverage rule as ids (genuine accessible-name sources — aria-label, label, placeholder — keep the relaxed whole-word rule, so the long-accessible-name heals are untouched); and `code`/`pre`/`kbd`/`samp` content is skipped at scan time. The /classattr shape is pinned twice: the contamination page refuses with honest intent-ambiguity naming the actual anonymous buttons — no selector strings anywhere in the reason — and the previously working heal is restored on a page where one button genuinely carries the name, healing cleanly to `getByRole("button", {"name":"Button","exact":true})` despite the same code samples alongside.

**Consent applies the previewed diff — never a re-probe.** Field report: the same broken locator was refused as ambiguous in one run and healed in another that passed `--yes`. The investigation confirmed `--yes` is read at exactly one site (the prompt skip) and that scan and run-first mode share one candidate pool, one scorer, and one ambiguity threshold — but consent (from `--yes` or the interactive prompt) used to trigger a complete SECOND heal() pass that re-opened the browser, re-probed, and re-decided; the applied and reported verdicts were the second pass's. If the page changed between the passes (deploy, SPA state, flaky content), the approved diff was silently replaced by whatever the re-probe concluded — reproduced deterministically against a page that mutates between loads (preview: healed; `--yes` run: refused, nothing applied). Consent now applies the PREVIEWED heal plan byte-for-byte (`HealResult.plan` + `applyHealPlan`): one probe, one verdict set, and the diff that lands is exactly the diff that was shown — which also makes applying faster, since the second browser session is gone. The 4-run matrix (scan/run-first × ±`--yes`) on a stable page is verdict-identical; mode differences in the field reduce to WHICH PAGE is probed (trace failure URL vs inferred route vs `--base-url`), which is documented behavior. Permanently asserted in the harness: every run-mode scenario invoking `--yes` first runs a no-yes preview and fails on any verdict divergence, and every static suite verifies the applied sources match the dry-run's previewed heals verbatim.

**ESM configs load the way Playwright loads them.** Real repos saw "playwright.config.js failed to load (SyntaxError: Cannot use import statement outside a module); falling back to goto() scan / --base-url" while Playwright itself loaded the same config fine — an ESM-syntax `.js` config in a package without `"type": "module"` parses as CJS under a naive `import()`, and every such run silently downgraded to the weaker fallback probe. Playwright's own config-loading machinery is not cleanly reachable from a user install (the `@playwright/test` exports map blocks its internals), so the loader now does what that machinery tolerates: on import failure, ESM-syntax configs retry under the ESM-forcing hook, which serves project (never node_modules) `.js` files as ES modules when — and only when — their source actually looks ESM, sniffed per file, so a genuinely-CJS helper imported by the same config still loads as CJS. All four config variants (CJS `.js`, ESM `.js` with `"type": "module"`, `.mjs`, `.ts`) plus the real-repo shape (ESM `.js`, no type field) and the mixed ESM-config-requiring-CJS-helper case are pinned as loading with no fallback line. The fallback survives only for genuinely broken configs, and its message now states both the underlying error and the cost: `…; falling back to goto() scan / --base-url — probing quality is reduced without the config (routes, baseURL, and storage state may be missing)`. The run-mode eval fixture's config is now an ESM `.js`, so every run-first scenario re-runs under one.

**Directory targets work, and file errors skip instead of crash.** Real case: `npx qa-core-heal tests/systematic` (a directory of 30 spec files) died in the probe phase with the bare "EISDIR: illegal operation on a directory, read" — the directory path flowed straight into `readFileSync`. Directory targets (the CLI positional, config `testDir`, and directory entries in heal's own API) are now WALKED, recursively, for `*.spec.ts/js` and `*.test.ts/js` files; only regular files are ever read — including surviving a directory whose *name* looks like a spec file — while symlinks are skipped for cycle safety and non-spec files ignored, both noted under `--verbose`. Every fs read in the gather path (spec files, followed page-object imports, `pageObjects.dir` entries) is guarded: a failure reports the full story — the operation, the exact path, and which spec was being processed — then the run continues with the remaining locators, closing with `N locator(s) skipped due to file errors` (per-target precise in run mode, per-file in scan mode; also carried in the `--json` payload as `fileErrors` and counted into `summary.errors`). A run-mode target whose source file was unreadable counts as a skip, not a "bug worth reporting". Tests pin the weird tree (26 specs across nested dirs, a spec-named directory, a symlinked dir that must not be followed), the exact real-world run-first directory shape, and a forced `EACCES` on one file skipping only that spec's locators.

**A proper CLI flag surface.** Parsing moved to Node's built-in `util.parseArgs` (no new dependency): `-h/--help` (usage, every flag with a one-liner, an example, and the explicit note that `-y/--yes` auto-approves EVIDENCE-BASED HEALS ONLY — suggestion-level changes will require a separate `--accept-suggestions`, future), `-v/--version`, `--verbose` (probe steps, candidate scoring, child commands — extra stderr lines only, verdicts and messages untouched), `--debug` (implies `--verbose`, adds stack traces and raw child stdout/stderr), `--output <path>` (tee the human report to a file, stdout unchanged), and `--no-color` (honoring the `NO_COLOR` env var automatically; output is colorless today, and the flag pins that it stays controllable). `--dry-run` now prints the exact would-be diff and states its contract — `dry run: no files changed, heal not verified` — while refusals behave identically to normal mode; `--config` failures already carried the full story and are now pinned. `--json` gained the schemaVersion 1 compatibility contract (see README): `verdicts` (spec, testTitle, classification, message, healApplied, before, after, verified) and `summary` ({heals, refusals, nonLocator, errors}) alongside the original fields, with errors also emitted as valid JSON carrying the failure story; exit codes unchanged. Unknown flags error with a `--help` hint. Zero-flag behavior is byte-identical to before, pinned by output snapshots captured from the pre-flag CLI; every flag has at least one test.

**Windows: the internal Playwright run works, and its failures tell the whole story.** On Windows, `qa-core-heal <spec>` died with "Could not run the Playwright tests (no JSON report)" while a direct `npx playwright test` worked. The internal run was spawned as `npx` behind `shell: true` on win32 — cmd.exe mangles the argv (the verify re-run's `--grep "title a|title b"` becomes a PIPE into a program named after the second title; paths with spaces lose their grouping) and depends on npx.cmd/PATH at all. All three child-run sites now resolve the project's LOCAL `@playwright/test` CLI entry and run it with the tool's own node executable — argv verbatim on every platform, no shim, no shell, no PATH — with npx (shell on Windows) kept only as a fallback when resolution fails; env, when passed, travels via the spawn options object, and the JSON report continues to be read from the child's stdout, so no temp-file path exists to get platform-specific. And a failed internal run can no longer hide its cause: the message now carries the exact command attempted, the spawn error code (ENOENT and friends) or exit status, and the child's stderr tail — the bare "Could not run the Playwright tests" shape is forbidden and pinned so. Tests pin the direct-CLI resolution, a `--grep` pipe surviving verbatim, the failure-message contents, and an end-to-end forced spawn failure (no local Playwright, empty PATH) surfacing command + ENOENT through the CLI.

**The warning filter classifies by family, not exact string.** Three leak shapes have now been seen from Node's in-process TypeScript loading (the Type Stripping / stripTypeScriptTypes experimental warnings, the "To load an ES module..." hint, and latest "Failed to load the ES module..." during auth-setup load) — each previously needing its own exact-string entry. The filter now classifies warnings into families by pattern: module-load/ESM interop hints (an "ES module" subject plus a load/parse verb, or the typeless-reparse code), experimental-feature notices about module machinery, and deprecation notices about module machinery — so a new phrasing of a known family is caught without a code change. Conservative by construction: anything outside the families passes through untouched, and the experimental/deprecation families require BOTH the warning type and a module-machinery subject, so warnings from the user's own test code or fixtures — their deprecations, custom warnings, or their app's own "experimental feature" notices — are never suppressed. Pinned: all three seen shapes filter, a fabricated fourth phrasing within a family filters, and a user-code warning passes through verbatim end-to-end (fresh-child-process fixtures, both typeless and commonjs package shapes).

**State-gated roles refuse with a widget-state explanation, never a heal.** Roles like `option`, `menuitem` (plus `menuitemcheckbox`, `menuitemradio`), `dialog`, and `tooltip` exist in the accessibility tree only while their widget is open — a fresh-load probe cannot see them, and the old generic no-candidate refusal read like the element never existed. A failing `getByRole` on a state-gated role that finds zero such candidates now refuses with the teaching message, the widget noun adapted to the role: `role 'option' elements exist only while a dropdown/listbox is open; a fresh page load cannot show them. Static probing cannot verify this locator - check the option name manually or re-record it.` (menu for the menuitem family, dialog, tooltip). The intent ladder is skipped and NO heal is ever proposed in this path — a fuzzy "match" against something else on the page would be the wrong element by construction — but the fuzzy scan's scored near-misses are kept and appended after the teaching line when any exist. Non-gated roles (`listitem`, `list`, …) keep the normal below-threshold near-miss refusal, and a gated locator that still RESOLVES (native selects keep their options in the tree) stays intact and untouched. Pinned by run-mode scenarios: a closed custom combobox whose options render only on open, and a plain listitem miss keeping the standard scored near-miss.

**Pointer-interception timeouts get a UX-defect verdict, never a heal.** A `locator.click` timeout whose call log shows the target resolved — visible, enabled, stable — with another element intercepting pointer events means the locator is healthy and healing has nothing to fix; worse, the overlay may be blocking real users too. Previously this classified non-locator with only the generic timeout line; it now gets the specific verdict, naming the interceptor from Playwright's own call log: `not a locator problem: another element (<div class="promo-overlay"></div>) is intercepting pointer events on the target. The selector is fine; this may be a real defect - an overlay blocking users.` Pinned by two run-mode eval scenarios modeled on the community tester's shared pages: a persistent invisible overlay produces the verdict with sources untouched, and an overlay that clears after 2s lets Playwright's own actionability retries absorb the wait — the test passes and run-first mode does nothing.

## 0.2.1

Fixes from real-world testing on uitestingplayground.com, in four batches. The eval harness closes the release at 52/52 heals, 20/20 refusals, 8/8 intact locators kept, 0 wrong heals across 13 suites (117 locators, 72 deliberately broken).

**Dashed tags hint, underscored tags heal (final batch).** A compound selector whose leading tag token is dashed (`button-1.btn.btn-primary`) may be a spec-legal custom element or a typo — undecidable from the page, so it is NEVER auto-healed, even when a corrected selector would match uniquely; the refusal replaces the generic hedge with a teaching hint that names the closest valid tag within two edits: `'button-1' may be a custom element (dashed tag names are spec-legal) or a typo; if it's a typo, correct it directly - closest valid tag: 'button'`. Underscores, by contrast, are illegal in ANY tag name, so an underscored token is always a typo: css-tag-fix now strips the underscore suffix and corrects one edit against the tag list (`buttons_1` → `buttons` → `button`), under the same guards (exactly one correction matching exactly one element, kind guard). Both pinned in the tag-typos suite, including the never-heal-dashed case on a page where the correction WOULD match uniquely.

**Prefix completion, token-anchored.** A truncated identifier heals to its single completion: `[name="search_f"]` → the `search_field` element, scored above the fuzzy band and below token containment. The signal is deliberately token-anchored — every word but the last must match exactly and only the final fragment completes (`search_f` = `search` + `f`→`field`); a single-word identifier gets no prefix signal, because `email` "completing" to `emailz9` is the hash-suffix trap, not a truncation (the existing near-miss pins forced this shape). Two completions (`search_field` / `search_filter`) refuse with both named. Single attribute selectors (`[name="..."]`, `[data-testid="..."]`, …) now carry their value as fuzzy identity, which is what lets the truncated attribute heal at all; pricing-hostile and hostile-mutation re-ran standalone and stay green.

**Expired storage state falls back to a configured auth setup.** When both are configured, the saved session is applied first — fast, runs no user code — and a probe redirected to a login-looking route prints `saved session expired; falling back to auth setup`, runs the login function (loud failure semantics unchanged), and retries the route. Never the reverse direction: a failing auth setup is a hard error, not an excuse to try stale cookies. Without an auth setup configured, the expired-session message is unchanged. This replaces the old rule where `--auth-setup` unconditionally displaced `--storage-state`; a valid session now wins outright (pinned by a tripwire test proving the login never runs when the session works).

**Duplicate-identity rot is now pinned.** The case a community tester predicted — a previously healed locator becoming ambiguous when the page later GAINS a duplicate identity — had no fixture. Now it does: heal on page v1, the fixture gains a second element with the same aria-label, and the next run-mode pass classifies the strict-mode failure and refuses with both candidates named (`candidates: #archive-order / #archive-copy`), never silently re-healing to either.

**Dynamic ids stay unproposed.** Verified working on uitestingplayground.com/dynamicid and pinned so it stays working: a per-load random (GUID-style) id, the locator mutated by role with `exact:true`, heals to `getByRole` with the exact name and `exact:true` preserved — and the random id is asserted NEVER proposed, because an id heal would pass its own re-run and break the next load (the self-certifying trap).

**Polish.** (a) The in-process auth-setup loader's warning filter had a coverage window: it was restored right after the module load, but the ESM-retry hooks run on a worker thread whose warnings (stripTypeScriptTypes, the ES-module hint) bypass the main thread's `emitWarning` entirely, and a login function's own imports resolve at call time — after the window closed. Reproduced with repo-shaped fixtures (typeless and `"type": "commonjs"` packages, each in a fresh child process, since warnings de-dupe per process) and fixed with a two-layer filter installed once for the life of the process: the `emitWarning` wrapper plus a stderr line filter that drops exactly the known noise shapes and nothing else. (b) `--auth-setup utils/common.ts:login` now works — `:` as the export separator, so zsh users need no quotes — and a `#` value pointing at a missing file suggests quoting in the error. (c) The harness column formerly labeled "final X/Y" is now "post-heal green", so suites whose expected refusals keep tests red stop reading as failures.

**Confirmation stability under churn.** A fingerprint read landing on a node detached mid-re-render returned a zero-sized box and could fake a geometry disagreement (a spurious "unstable" refusal on interval-re-rendering pages); detached reads now throw into the existing retry instead of counting as evidence.

**Zero-found count/existence assertions classify as locator failures.** Real case: a test asserting `expect(locator).toHaveCount(1)` on a selector matching nothing was reported as "not a locator problem, healing won't fix this" — the classifier's found-element gate (`locator resolved to ...`) swallowed toHaveCount's own call-log line `locator resolved to 0 elements`. An actual count of 0 means nothing matched, which is the definition of a broken locator; the same broken selector already classified as a locator failure when an ACTION hit it first, so classification depended on which line of the test ran first. Expect failures on count/existence matchers (`toHaveCount`, `toBeVisible`, `toBeAttached`, `toBeInViewport`) are now locator failures whenever the error shows zero elements found (the `locator resolved to 0 elements` call-log line, a bare `Received: 0`, or the already-recognized `element(s) not found`). Count mismatches with actual > 0 (found some, wrong number) and value matchers on found elements (`toHaveText` and friends) stay non-locator, pinned by regression tests on real Playwright 1.60 message shapes and three new run-mode eval scenarios: `toHaveCount(1)` on nothing classifies-heals-re-runs-green, `toHaveCount(1)` on two elements stays non-locator with sources untouched, and a found-element `toHaveText` mismatch stays non-locator.

**Tag-typo correction for compound CSS selectors (level `css-tag-fix`).** Real case: `locator('buttons.btn.btn-primary')` refused with the generic not-found hedge while the page had exactly one `button.btn.btn-primary`. Compound selectors stay excluded from intent/fuzzy matching — their classes are styling, not identity — but an invalid tag token is recoverable evidence of a pure typo. When a compound selector fails and its leading tag token is not a valid HTML/SVG element name, corrections at edit distance 1 against the known tag list are probed (`buttons`→`button`, `imgs`→`img`, `divv`→`div`); if exactly one correction resolves to EXACTLY ONE element on the failure page and passes the kind guard, the proposed heal is the corrected compound selector itself (`page.locator("button.btn.btn-primary")`, level `css-tag-fix`) — never a reinvented locator. Two+ matches, zero matches, competing corrections, a valid tag, or a dashed custom element: refuse as before. The stage opens compound selectors to nothing else. Locked by the new `tag-typos` eval suite (heals on a one-button page, refuses on a two-button page, refuses a valid-tag compound matching nothing) plus a run-mode scenario reproducing the full real-world flow (`toHaveCount(1)` + tag typo → healed → green); pricing-hostile and hostile-mutation re-run standalone and stay green.

**Candidate collection sees into open shadow DOM (batch 3).** Real case (uitestingplayground.com/shadowdom): `locator('.buttonGenerate')`, mutated from `#buttonGenerate`, refused with closest candidate "GUID Generator:" (0.50) — the page's light-DOM heading — proving the shadow-root button never entered the candidate set. Playwright locators pierce open shadow roots natively, so users' tests work there and the healer must too. The candidate scan now recurses into every open `shadowRoot` (nested roots included, breadth-first, capped), collecting the same identity evidence as light DOM; `label[for]` association is resolved per root, since `for=` scopes to its own tree. An audit confirmed no other raw `querySelector` path exists — same-element confirmation, fingerprints, kind reads, tag-fix probes, and ambiguity descriptions are all Playwright-locator/handle-based and already resolve through shadow boundaries. Closed shadow roots remain inaccessible by design (to Playwright as well); because a closed root is undetectable after creation, an init script wraps `Element.prototype.attachShadow` in the probing context to record `mode:'closed'` attachments, and a not-found refusal on such a page appends: "this page contains closed shadow roots the probe cannot inspect". Locked by the new `shadow-dom` eval suite: `.buttonGenerate` heals to `#buttonGenerate` inside an open root end-to-end with a green re-run, a shadow-in-shadow field heals through nested roots, and the closed-root fixture pins the appended refusal note.

**Confirmation understands every identifier spelling (batch 2, highest priority).** Real case: `page.locator('.ajaxButton')` re-resolved to the right element — button#ajaxButton, the sole candidate — and same-element confirmation refused anyway: the matcher compared the spaced intent token ("ajax Button") against the element's glued camelCase id ("ajaxButton"), and both existing normal forms lowercase BEFORE any split, destroying the camel boundary. The same normalization bug class the churn fix solved, alive in another corner. Every comparison site in the confirm/fingerprint path was audited: all identity matching goes through one predicate, which now also compares a camel-aware canonical word sequence — glued, snake_case, kebab-case, camelCase, and spaced forms of an identifier are all the same identity. (The fingerprint-agreement check deliberately stays raw equality: it compares two reads of the same locator with itself, where any difference means the element changed.) The unstable-evidence and hostile-mutation protections are untouched. Locked by the new `normalization` eval suite: `.ajaxButton` heals to the button with the camelCase id — the id/class-swap mutation — end-to-end with a green re-run.

**Exact identifier equality breaks fuzzy ties.** Real case: `page.locator('.content')` refused as "ambiguous: several close matches (#content, #footer-content)". "content" IS the whole id of #content and only a sub-token of footer-content — not a tie. When several candidates clear the fuzzy band, exact equality of the (stripped) identifier with a candidate's id / name / data-testid now outranks token containment and picks the winner; the kind guard and same-element confirmation still apply downstream. Two candidates BOTH exact-equal after normalization (e.g. #search_box vs #searchBox) remain a genuine tie, refused with exactly those named. Unit tests pin all four shapes; the normalization suite heals `.content` to `#content` on a page that also has #footer-content and refuses the both-exact counter-case.

**Prettier-wrapped locators match to source, with every getByRole option.** Real case: a failing `getByRole('link', { name: 'Button Triggering AJAX Request', exact: true })` existed verbatim in the POM, yet run mode reported "could not be matched to source ... This is a bug worth reporting". Reproduced faithfully: the source parser was LINE-based, and any locator call whose options object is wrapped across lines — which prettier does to precisely these long getByRole calls — parsed as nothing. The parser now scans whole sources: wrapped calls are found, matched, healed, and written back as a single-line replacement of the full span. The canonical structure used for runtime-vs-source comparison now also covers ALL getByRole options (checked, disabled, expanded, includeHidden, pressed, selected, level) in a fixed key order — insensitive to property order, quote style, and boolean representation, with `exact:false` canonically equal to absent (Playwright's default) while `checked:false` stays meaningful (an unchecked checkbox is an assertion, not an omission). And when a getByRole with `exact:true` re-resolves to an element carrying the IDENTICAL exact name under a different role, the role is treated as the corrected hypothesis (link → button): the kind guard no longer vetoes the fix — the exact accessible name is the identity, the role was the broken part. Token-derived kind expectations (`#export-button` must be a button) still refuse exactly as before. A new run-mode eval scenario pins the whole real-world shape: multi-line POM locator, mutated role, matched, healed back to the button role, green re-run.

**Deleted positional disambiguators refuse and teach, never guess.** Real case: `.first()` removed from `getByRole('button', { name: 'Button', exact: true })` — the locator strict-fails against 3 buttons identical by accessible name. Captured current behavior first: the failure classified as a locator problem (correct) but the probe counted 3 matches and reported the locator INTACT — exit 0, "nothing to heal", test still red. A guessed `.first()`/`.nth()` would be worse: it passes the re-run while silently changing which element the test verifies — a self-certifying wrong heal. Strict-mode evidence now survives classification into the probe: a strict-failure locator that matches several elements on its failure page refuses with a teaching message naming what distinguishes the matches (id, data-testid, or the classes not shared by every match): "locator matches 3 elements identical by accessible name; the original disambiguator (.first()/.nth()) cannot be recovered safely. Add a positional call back, or target by a distinguishing attribute (candidates: .plan-basic / .plan-pro / .plan-max)". A run-mode eval scenario pins the refusal, the candidate list, and that no positional call is ever proposed.

**Compound-selector refusals teach the fix.** When a compound CSS selector is refused for lacking identity (no-identity and not-found refusals, scan and run modes), the reason now appends: "compound CSS selectors carry little recoverable identity (utility classes describe styling, not which element this is); consider getByRole or a data-testid". Existing pinned refusal reasons are unchanged — the appendix only fires for compound CSS selectors, and every previously pinned refusal is on a simple selector or a non-CSS locator.

## 0.2.0

**Run-first healing is the new default.** `qa-core-heal <spec>` now runs the spec with Playwright before touching anything. All tests green prints "All tests passing. Nothing to heal." and exits 0 — no scanning, no probing, no browser launched. On failures, each one is classified from the JSON report: locator failures (a timeout waiting for a locator, an element not found, a strict mode violation) are heal candidates; everything else — an assertion value mismatch on an element that WAS found, a navigation or network error, a thrown app error — is reported as "not a locator problem, healing won't fix this" with the failure line, and never healed. For each locator failure the CLI extracts the failing selector from the error message and the page URL the test was on when it failed from the Playwright trace (tests run with `--trace retain-on-failure`), then probes ONLY those selectors on those pages — the same heal pipeline and refusal rules as always. After the usual diff-and-confirm, only the previously failing tests are re-run to verify, and applied heals land in the audit log with the verified flag.

Because run-first probes the page a test was actually on when it failed, it can heal locators the static probe honestly cannot: an element on a page only reached by clicking through (no `goto()` ever names it) refuses under the static probe and heals under run-first — locked by a new eval scenario, alongside passing-suite-means-zero-probing, locator-failure-heals-and-re-runs-green, and assertion-failure-is-never-healed.

**The static probe moved behind `--scan`.** No test execution, every locator in the spec and its page objects probed on its inferred route, current output — for locator audits and suites too expensive to run.

**Prompt input fix.** The apply prompt accepts y/Y/yes, declines on n/no/empty, and re-prompts on anything unrecognized instead of silently treating it as "no". The `--yes`/`-y` flags and the exit-code contract are unchanged (0 success, 1 error, 2 heals available but not applied; "all tests passing" is a 0).

**Failing selectors are matched to source structurally, never textually.** Playwright renders a failing locator its own way (`getByRole('textbox', { name: 'Emails' })`) while the source may say `page.getByRole("textbox", {"name":"Emails"})` — quote style, spacing, quoted-vs-bare option keys, receiver prefix all differ. Both sides now parse into a canonical structure (method + role/selector + options) and compare structurally, so formatting can never make a detected failure silently match nothing. The failure's stack trace is the primary targeting signal: the structurally-matching locator call nearest the error's source location wins (Playwright errors carry the file:line of the action call), with structural matching across the whole import graph as the fallback — which is how a failure raised in a spec heals the locator defined in an imported page object. When neither signal finds the call, the CLI never claims "Nothing to heal" while tests are red: it prints `1 failing locator could not be matched to source: <selector> (from <test title>). This is a bug worth reporting.` and exits 1 (the `--json` payload lists these under `unmatchedFailures`). A run whose Playwright report contains zero tests is likewise an error, not a clean bill of health. New eval scenarios pin the three matching shapes end-to-end: a broken locator living in an imported page object, a getByRole with an options object across the quote/spacing mismatch, and a plain CSS locator().

**Config loading matches Playwright's ESM/CJS interop.** Real-world configs mix ESM imports with `require("dotenv").config()`; Playwright's loader supports that, but the child-process native import parsed the file as ESM where `require` is undefined, threw ReferenceError — and the loader swallowed it, wrongly reporting "no baseURL". The child loader now exposes a CJS-compatible `require` (created against the config's own path, so it resolves the user's node_modules) before importing, loads genuinely-CJS configs (`module.exports`, no import/export syntax) via `require()` directly instead of `import()`, and preloads `.env` from the config's directory without overriding already-set env vars (configs that load dotenv themselves now simply work). The loader's result travels on a dedicated pipe (fd 3), so a config — or dotenv's own logging — writing to stdout can never corrupt it. Diagnostics are now mandatory: a config that throws or times out produces a warning with the underlying error ("playwright.config.ts failed to load (ReferenceError: require is not defined); falling back to goto() scan / --base-url") — absence is never reported when the truth is failure. Project-level baseURLs: when a config's projects agree on one baseURL it is used; when they disagree, the CLI warns and the new `--project <name>` flag chooses. Regression fixtures pin the exact ESM+require+dotenv+conditional-reporters pattern, a pure-CJS config, the throwing-config warning text, project disagreement, and env-var precedence.

**Classification is evidence-based, not message-shape-based.** Real case: a locator wait outlived the TEST timeout, teardown closed the browser, and the pending action died with "Target page, context or browser has been closed" — the top-level error said only "Test timeout of 30000ms exceeded" and the run was misclassified as non-locator. All errors of a failed result are now collected (on a test timeout the pending locator action arrives as a secondary error) and a failure is a locator failure whenever the evidence exists ANYWHERE in it: a `locator.<action>:` / `expect.<matcher>:` prefix or a call-log "waiting for locator/getBy..." line, regardless of the top-level message. The selector comes from the call log; source locations come from every error's location and project stack frames (node_modules skipped). The one earlier gate stands: a locator that RESOLVED to a real element stays non-locator. A timeout with no locator evidence anywhere reports "timed out with no pending locator action".

**Failure-URL fallback chain for custom browser setups.** Manual `chromium.launch()` in beforeAll can produce no usable trace, leaving the failure URL unknown. The chain is now: trace, else the statically inferred route for that locator (its file's goto/override/inherited routes — the bare base-URL fallback no longer counts as a route signal), else an explicitly given `--base-url`, else a loud refusal: "could not determine the page where \<selector\> failed (custom browser setup produces no trace); re-run with --route \<file\>=\<route\> or --base-url". The wrong page is never probed silently. A new `--no-trace` flag skips tracing entirely for setups where it is unavailable or unwanted. Page-object imports are now followed recursively, so a locator defined in a widget two imports below the spec is matched and healed. Three new run-mode eval scenarios pin all of this: the timeout+closed shape classified and healed, a manual-browser spec healing via route inference, and a two-imports-deep POM locator healing end-to-end.

**Trace URLs come from the MAIN frame, with sanity checks.** On a Vercel-hosted app the extracted failure page was the vercel.live feedback widget — a child iframe whose snapshot happened to be the last one in the trace. Extraction now uses the trace's isMainFrame flag (last main-frame snapshot wins; a missing flag from older trace formats counts as main) and skips non-http URLs like about:blank and chrome-error://. On top of that, a trace URL whose origin matches neither the resolved base URL nor any goto()/--route target is discarded with a stderr message saying why, falling back to route inference — the wrong page is never probed. The run-mode fixture now embeds a different-origin iframe (with a mutation loop that deliberately makes its snapshot the LAST one recorded) and asserts the extracted URL is the main page.

**Config loading survives CommonJS package contexts.** The same real-repo config that previously hit "require is not defined" then failed with "SyntaxError: Cannot use import statement outside a module": in a package whose package.json has no "type" field (or says "commonjs"), some Nodes execute a stripped .ts config as CJS, where its import statements are illegal. The loader now always tries native import() first (require shim installed); when that fails for a .ts config it retries with an ESM-forcing load hook (module.register + stripTypeScriptTypes) that serves the file as a stripped ES module regardless of package type; the createRequire fallback is reserved for files with no import/export syntax; and when every attempt fails the diagnostic reports each attempt's error. Two more real-world fixes fell out of reproducing this faithfully: the earlier fixture had no package.json at all (inheriting "type": "module" from this repo — why it passed while reality failed), and dotenv's tip line — which itself contains a "{" — printed ahead of Playwright's JSON report, breaking the naive report slicing; report parsing now scans for the actual report object. Regression fixtures: the byte-for-byte config in a typeless package AND under explicit "type": "commonjs" (deterministic on every Node), both-errors diagnostics, and an end-to-end run-mode heal through the exact CLI code path with a relatively-navigating spec, where healing is impossible unless the config's baseURL truly resolves.

**Type-only named imports survive the ESM retry.** A config importing a TypeScript type as a plain named import ("import { defineConfig, devices, ReporterDescription } from '@playwright/test'") crashed the ESM retry with "does not provide an export named 'ReporterDescription'": type stripping removes annotations but does NOT elide type-only import specifiers written without the `import type` keyword. The retry hook now rewrites every named import (including default+named mixes) to a namespace import plus destructuring — a missing export destructures to undefined, which is harmless because a type identifier is unused after stripping. Regression fixture: that exact config shape in a "type": "commonjs" package, resolved at the loader level and healed end-to-end through the run-mode CLI path.

**The trace URL is trusted when nothing else exists.** The origin sanity check discarded a correct main-frame failure URL precisely when it was most needed: the config had failed to load, no baseURL resolved, so there was nothing to compare origins against — and the run died with "could not determine the target URL" while holding the right answer. The origin check now only applies when an anchor exists (a resolved baseURL or an absolute goto()/--route target); with none, the main-frame trace URL — which already passed the non-http and child-iframe filters, which always apply — is trusted, the base URL is derived from its origin, and the output notes "using failure page from trace: \<url\>". A new run-mode eval scenario locks it: a config Playwright loads but heal cannot (a TS enum defeats type stripping), a spec that only navigates relatively, and a heal that succeeds purely from the trace URL — alongside the load-failure warning.

**Authenticated probing via --storage-state.** On an auth-gated app, run mode classified the failure and extracted the right failure URL, but the unauthenticated probe got redirected to the login screen and refused against the wrong page — everything worked except auth. `--storage-state <path>` (and the existing qa-core.config.json `auth.storageState`) now applies Playwright's storageState to the probing context in both run mode and `--scan`. When neither is set, heal auto-detects in priority order — `use.storageState` from the playwright config (top-level or agreed across projects), then the conventional `.auth/state.json` and `playwright/.auth/user.json` — announcing "using storage state from \<path\>"; detection finding nothing just probes unauthenticated as before. Probes are now redirect-aware: a page that lands somewhere other than the requested URL is NEVER probed as if it were the target. The output says "requested /accounts, landed on /login (redirected)", adds "the page may require authentication; pass --storage-state \<path\>" when no session was used and the landing page looks like a login route, or "storage state was applied but /accounts still redirected to /login; the saved session may be expired. Re-generate it and retry." when one was — and the locator refuses with the redirect named. Storage-state file contents never appear in heal output or the audit log; only the path is logged. Ambiguity refusals now NAME their candidates (capped at 5): "several elements match the intent (candidates: #alpha, #beta, #gamma), refusing to guess". A three-part eval scenario locks the feature against a fixture server that 302-redirects /app to /login without a session cookie: unauthenticated refusal with the redirect and hint, an end-to-end heal with a valid saved session, and the expired-session message with a stale one.

**--auth-setup: authenticated probing via the user's own login code.** Complementing --storage-state: `--auth-setup <file>#<export>` (default export when #export is omitted; also `authSetup` in qa-core.config.json) points at the project's existing login helper. Heal loads the module with the same TypeScript machinery as the config loader — require shim, ESM-forcing retry, in-process because the function needs the live page — and calls `await fn(page)` on a fresh page in the probing context before probing, in both run mode and --scan. It deliberately does NOT parse or re-execute beforeAll/beforeEach hooks: setup code can seed data or trigger side effects, and only the user can say what is safe to re-run. A login that throws or hangs (60s default, `--auth-setup-timeout <seconds>`) fails the run loudly with "auth setup \<file\>#\<export\> failed: \<error\>" — probing unauthenticated is never a silent fallback. `--auth-setup` takes precedence over `--storage-state` (with a note), the single probing context carries the session across every probed route (one login, many probes), and redirect detection stays live with its own diagnosis: "auth setup ran but /accounts still redirected to /login; the login function may have failed silently or the session did not persist". Only file paths, export names, and pass/fail are logged; credentials, cookie values, and storage contents never are. The auth eval fixture gained a POST /api/login endpoint and a three-part scenario: a real login function heals end-to-end, a throwing one fails loudly with nothing probed, and a silently-failing one gets the redirect-after-auth message. The README's Authenticated apps section now carries the decision guide: --auth-setup pointing at your login helper (recommended), --storage-state for saved sessions and CI, and the save-auth script pattern.

**Confirmation is churn-tolerant and its refusals are debuggable.** A correct heal ([name="search_field_1"] → the page's [name="search_field"]) was refused with a bare "re-resolved to a different element". Reproducing on an interval-re-rendering page failed 10/10 — deterministically, which pointed past the node-churn hypothesis to the real root cause: the confirmation matcher compared the spaced token ("search field 1") against the raw attribute ("search_field") and separators never matched. Matching now compares separator-normalized forms too (underscores/dashes/spaces are the same identity word sequence). Churn tolerance was layered in as well, since the repro also proved nodes get replaced mid-probe: a failed confirmation attempt retries once after a 250ms settle, and then a fingerprint pass takes over — two FRESH locator reads compared as logical identity (tag, key attributes, accessible-name sources, geometry within 5px) rather than node identity, so a React re-render replacing every node cannot fail a correct heal. Genuine mismatches still refuse, and the refusal finally names what differed: "re-resolved element differs: expected an element matching \"search panel 42\" (from page.locator('#search-panel-42')), got input\[id="global-lookup"\]\[type="search"\] at (x, y); not healing". The pinned-handle mutation-watch protections are untouched — the hostile-mutation suite still gets its deterministic instability refusal. A new react-churn eval suite locks both sides: the heal surviving 150ms-interval node replacement end-to-end, and a genuinely different control refused with the diff named. (Fixture note: the suite lives on port 4191 because 4190 is on the fetch-spec bad-ports list — Chromium and undici both refuse it.)

**The probing context carries the resolved base URL.** Login helpers written for Playwright test contexts navigate relatively (`page.goto("/")`) and rely on use.baseURL; the probing context did not set it, so --auth-setup died with "Cannot navigate to invalid URL". The context is now created with `baseURL` set to whatever resolution produced (config / trace-derived / --base-url) — always, not just for auth-setup, so relative navigation anywhere in probing resolves like it does in the user's tests. If a future path ever probes without a resolvable base and a login helper then fails on relative navigation, the failure says: "your login function navigates to a relative URL but no baseURL could be resolved; pass --base-url". The auth-setup fixtures now navigate relatively on purpose, pinning this.

**In-process module loading is warning-free.** The child-process config loader suppresses Node's TypeScript noise with --no-warnings, but the in-process auth-setup loader leaked ExperimentalWarning (Type Stripping / stripTypeScriptTypes) and module-type warnings into CLI output. A process-warning filter now drops exactly those warning shapes for the duration of the load and restores the original emitter after; the auth-setup success test asserts the real stderr stream is clean of them.

**Token containment, glued digit suffixes, and render-random ids.** A deterministic refusal on a React SPA: getByRole("textbox", {name:"search1"}) refused every run with a near-miss naming "_r_NN_-form-item" — a different render-random id each run. Verified on a modeled fixture: the field's FULL accessible name is "Search by account or login" (Playwright name matching is substring, which is why a prior heal to name:"search" resolved green), whole-string fuzzy scoring of "search1" against it lands far below the bar, and the glued digit could not strip ("search1" is one word). Four fixes: (1) suffix stripping now handles digits glued to the word — search1 → search, email2 → email — so the ladder retries the stripped name first; (2) token-containment scoring — a stripped identifier matching a whole word of a candidate's accessible name scores above the fuzzy band (below exact); for id/name/testid values the identifier must also cover at least half the value's meaningful words, so "result" inside "newsletter-result-block" is NOT identity (the wrong-heal trap of widening id matching, pinned by a unit test); two candidates containing the token refuse as ambiguous with both named; (3) render-random identifiers (React useId patterns like _r_17_-form-item / :r1a:, and all-hash values) contribute nothing to matching and are excluded from refusal naming; near-misses now name the top 3 candidates with scores ("closest candidates below the confidence threshold: #emailz9 (0.71)"), falling back to a generated id only when nothing else exists; (4) hardening: a mutation-quiet settle (150ms quiet, capped at 2s, `--settle-ms` to change, 0 disables) runs before candidate collection, noting "candidate collection may be incomplete" when the cap is hit. Same-element confirmation and the element fingerprint now read the ASSOCIATED LABEL text (el.labels) — for label-for inputs that is the accessible name, and often the only human identity the element carries. New eval cases: the long-accessible-name heal and a two-field token-ambiguity refusal, both on Mantine-style markup with useId ids. pricing-hostile was run specifically to confirm token containment re-opens none of the hostile intent-widening cases.

In `--json` run-first output, the payload gains a `nonLocatorFailures` array listing the failures healing cannot fix.

## 0.1.5

Two gaps found in real testing, plus CLI ergonomics.

**CI-friendly apply.** `--yes` gained a `-y` alias. When stdout is not a TTY (or with `--json`) the CLI never prompts: with `--yes` it applies; without it the run becomes preview-only — the full proposed diff still prints — and exits with code **2**, meaning "heals available but not applied", so pipelines can detect actionable heals without ever writing files by accident. Declining the interactive prompt exits 2 as well. Exit codes are now documented: 0 success (applied, nothing to heal, or `--dry-run`), 1 error, 2 heals available but not applied. In `--json` output, `dryRun` is now true whenever the run wrote no files.

**Readable multi-file output.** Per-locator lines (broken / healed / unhealable with reason) are grouped under the source file they live in — one block per spec or page object instead of a flat stream — with the totals kept at the end.

**Fuzzy and suffix-strip now cover semantic identities, not just CSS.** The typo pipeline used to apply only to simple `#id` / `.class` / test-id selectors, so `page.getByRole("textbox", { name: "Ema_il_2" })` refused even though normalized "email2" is 0.833 similar to "Email" — above the 0.8 bar. The string identity of semantic locators — the getByRole name, getByLabel, getByPlaceholder, getByText, getByTitle, getByAltText strings, and the `{ hasText }` filter on locator() calls — now runs through the same pipeline in the same order: the identity as written, a humanized form (separators and camelCase to spaces), the auto-suffix-stripped form, then fuzzy; every candidate still faces the kind guard, the ambiguity rules, and same-element confirmation. To let text identities match, the fuzzy page scan now also collects the visible text of leaf elements (label elements excluded — their text already counts as the identity of the control they label). The real case heals on the live shop: the mutated role name resolves to getByRole("textbox", { name: "Email" }) on /login, and a mutated role name whose normalized form sits equally close to two inputs refuses as ambiguous with both candidates named (both pinned in the eval suites). The hostile fixtures were measured before enabling this: their reworded texts score 0.21–0.66 against the retired strings, safely below the heal bar, and they stay refused.

**Never-found refusals now say only what the engine actually knows.** The state-dependent phrasing used to fire as a catch-all whenever an element was missing and nothing similar existed, which produced a false explanation for plainly static elements. The wording is now a hierarchy: a below-threshold fuzzy near-miss keeps the "closest candidate X below confidence threshold" reason; a selector token that names an after-action UI pattern (toast, modal, alert, result, notification, snackbar, dialog, popup, confirmation, flash) is positive evidence and refuses with "element may be state-dependent (selector token \"result\" suggests it appears only after user actions); static healing cannot verify it"; with neither, the refusal hedges honestly: "not found on route /login: no matching or similar element on the probed page. The element may have been removed, renamed beyond recognition, or may only appear after user actions." The pinned .result eval reason moved to the evidence-carrying wording.

## 0.1.4

Everything below shipped together in 0.1.4 (an internal 0.1.3 was never published). The work came from healing a real multi-page POM project against `https://demowebshop.tricentis.com`, then testing the result in anger.

**Base URL resolution.** The CLI demanded --base-url even when the target project already declared its base URL. It now resolves the URL in priority order: an explicit --base-url / qa-core.config.json baseUrl, then use.baseURL from the project's own playwright.config.ts/.js — actually imported (defineConfig runs and env vars evaluate; no text scraping), then the first absolute page.goto() in the specs. Only when all of those fail does it ask for --base-url. Relative goto() routes are joined with the resolved base URL. The config import runs in a child Node process launched with --no-warnings, so the noise Node prints when loading TypeScript (ExperimentalWarning: Type Stripping) or a typeless package.json (MODULE_TYPELESS_PACKAGE_JSON) never reaches the CLI output, and a config that throws cannot take the run down. TypeScript configs need Node's native type stripping: the package now declares engines.node >= 22.6, and on older Node the CLI exits with "qa-core-heal requires Node 22.6+ to read TypeScript configs. Detected \<version\>. Workaround: pass --base-url and --route flags." — but only when the .ts config is actually the thing standing between it and a base URL; .js configs and explicit flags keep working.

**Per-locator page context.** Every locator used to be probed against a single page (the base URL), so locators living on other routes came back "could not be re-resolved" or "ambiguous" — and could even heal to a same-named element on the wrong page. Each locator is now probed on the route its spec navigates to: routes are inferred from page.goto() calls (nearest goto above the locator, else the file's first), page objects with no goto inherit the routes of every spec importing them, and a page object shared by specs with different routes is probed on each route and healed only when all routes agree on the same replacement. Specs are healed jointly in one pass, so shared page objects are scanned once instead of once per importing spec. A new repeatable `--route <file>=<route>` flag overrides the inference per file. Refusals now say where the engine looked: "not found on route /login: could not be re-resolved there" is distinct from "ambiguous on route /login: several elements match the intent, refusing to guess" and from "candidates disagree across routes (...); refusing to guess".

**Element-kind guard.** Real case: #register-button — a submit button on /register — was healed to getByRole("link", { name: "register" }), the nav link in the header. The engine now infers the expected element kind from the original selector (whole-word tokens like button, link, input, checkbox in ids/classes, the getByRole role, and the API used on the locator: .fill implies a text input, .check a checkable, .selectOption a select) and reads the candidate's actual kind from the live element. A definite conflict refuses with "kind mismatch: expected button, candidate is link" instead of healing. A refusal here is correct behavior; the engine never guesses across kinds.

**Typo'd identifiers heal through a fuzzy stage.** `#Emai_l` (a typo of `#Email`) used to refuse: its tokens never match "Email" semantically, and the auto-suffix retry (which handles renamed generated ids like "#Email_1" by stripping the trailing fragment) does not cover in-word typos. A new fuzzy stage — running strictly AFTER exact and suffix-stripped intent matching fail, so it always scores lower — normalizes the broken identifier to bare lowercase alphanumerics and scores it against the page's ids, name attributes, and accessible-name sources (aria-label, associated label text, placeholder, test ids) by edit-distance ratio with adjacent transpositions counted as one edit. A single candidate at or above 0.8 similarity heals, still subject to the element-kind guard, the ambiguity rules, and same-element confirmation; two candidates in the band refuse as "ambiguous on route X: several close matches (#a, #b), refusing to guess"; a candidate below the bar is named honestly: "not found on route X: closest candidate \"#Email\" below confidence threshold". Fuzzy only considers simple `#id` / `.class` / test-id selectors — a compound selector names a position, not an identity.

**State-dependent elements are documented, not forced.** `.result` on /register exists only after the form is submitted; static probing can never see it and its refusal is CORRECT. Such never-found locators now refuse with a distinct reason — "element may be state-dependent (appears only after user actions); static healing cannot verify it" — and the README gained a Limitations section explaining this honestly, with runtime healing (probing at the moment a selector fails mid-test) as the planned answer.

**Refusal reasons are printed in every mode.** The default (apply) mode ran its preview probe silently, so a run that ended in refusals printed only "Nothing to heal ... N refused" with no detail, while --dry-run showed full reasons. The preview pass now prints the same per-locator lines as dry-run — intact, healed, and unhealable with the reason — in all human modes; the confirmed write pass no longer re-prints them. JSON output is unchanged.

Eval coverage grew from 6 to 8 suites (70 locators, 34 deliberately broken), including demowebshop-pom, which runs against the live Tricentis demo shop: base URL only in playwright.config.ts, #Email_1 and #Emai_l both healing to getByRole("textbox", { name: "Email" }) on /login, #register-button pinned as intact and never healed to a link, and .result pinned as refused with the exact state-dependent reason. The new fuzzy-typos suite pins the fuzzy kind-conflict refusal and the close-match ambiguity refusal. A node:test unit/integration suite (npm test) covers the config loader, the Node version gate, route inference, fuzzy scoring, the kind guard, and CLI output. Final scoreboard: 25/25 heals verified by passing re-runs, 9/9 refusals with the expected reasons, 1/1 intact locator untouched, 0 wrong heals.

## 0.1.2

Fixed a nondeterministic heal verdict on pages that rewrite identity attributes on a timer. On a page where two buttons swapped their id and title attributes every millisecond, the engine found the right element on every run, but the final confirmation read the element's attributes at a single instant, so the verdict depended on which phase of the swap that read landed in: some runs healed, others refused, from the same command on the same page.

The confirmation now pins the element once, reads its identity evidence twice over a short window, and watches for mutations in between. Any evidence that changed during the window is discarded before the match runs, including values the mutation watch saw pass through between the two reads. Stable evidence confirms exactly as before, so all previous eval results are unchanged. When the only evidence that would have matched was unstable, heal now refuses deterministically with the reason "element identity attributes are unstable; cannot confirm the match" instead of guessing.

A new eval fixture, hostile-mutation, locks the behavior: ten consecutive dry runs produce byte-identical output. The bug was found via a community challenge page.
